# Outbox atomicity register — INV-OUTBOX-SURVIVES-CRASH
#
# Each line is a file containing domain-event enqueues that are NOT inside a transaction, and how many.
# Every one is a place where a state change can outlive its event: EfOutbox.EnqueueRawAsync commits on its
# own SaveChanges, so a process kill between the business commit and the enqueue leaves the change durable
# and the event gone, with nothing recording that it was owed. Enqueue-before-save is the mirror failure —
# an event for a change that never committed, which cannot be un-sent.
#
# THE DEBT IS ZERO. This file opened at 73 sites across 30 files and every one of them has been closed by
# putting the write and its event in one transaction. What is listed below is NOT debt: each remaining entry
# is an enqueue with NO LOCAL STATE CHANGE BEHIND IT — the event is the entire write, so there is no second
# commit for a crash to fall between and nothing a transaction would make more atomic. They are listed
# because the rule is deliberately write-agnostic (see below), so the detector cannot tell them apart from
# the real thing, and an unexplained exemption is how an allow-list turns back into debt. Each one carries
# its reason. Adding a line here needs the same argument, in writing.
#
# THE RULE DOES NOT REQUIRE A VISIBLE WRITE, and that is deliberate. An earlier version only flagged an
# enqueue that shared a handler with a SaveChangesAsync. In emr, pharmacy dispensing, orders consume and
# every claims endpoint the state change happens inside a SERVICE that owns and commits its own transaction,
# and the handler enqueues after it returns — the exact two-commit shape this rule forbids, with nothing in
# the handler for that detector to find. It was blind to 40 sites, concentrated in the money paths, and the
# register read as though they did not exist.
#
# OutboxAtomicityTests ratchets these numbers ONE WAY:
#   * a file not listed here may have ZERO such sites
#   * a listed file may shrink or disappear, never grow
#   * a stale entry (a file already fixed) is itself a failure — it would re-permit a regression
#
# Where the handler does the write: wrap the state change and its enqueue(s) in one
# `await using var tx = await db.Database.BeginTransactionAsync(ct); ... await tx.CommitAsync(ct);`
# An early return before the commit rolls both back, which is the correct outcome.
#
# Where a SERVICE does the write: the enqueue has to move inside that service's transaction — wrapping the
# handler would nest a second transaction inside the service's own and throw. Where a service takes an
# ambient transaction (MembershipCommands) or an `insideTransaction:` callback (pharmacy's DispenseExecutor,
# emr's AppointmentTransitions), the handler joins that one instead of opening a second.
#
# Format: <repo-relative-path> <count>
