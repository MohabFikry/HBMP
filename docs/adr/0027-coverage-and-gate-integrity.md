# ADR-0027 — Coverage measurement integrity: the denominator was wrong, the floors were not

**Status:** Accepted · **Date:** 2026-07-30 · **Phase:** 24, Gate 0
**Deciders:** HBMP platform / quality
**Supersedes:** nothing · **Amends:** the measurement in `tools/ci/coverage-gate.sh` (18.E1)

## Context

CI reported a coverage collapse:

```
overall  47,920/186,464 = 25.7%   (floor 45)   FAIL
domain   10,620/22,625  = 46.9%   (floor 58)   FAIL
```

The floors are documented as a regression guard *set below the value measured when they were written*, so
this read as a genuine fall from >45% and >58% — plausibly explained by phases 19–21 (claims, profile,
callcentre, admin) landing while the pipeline died at an earlier gate and nobody could see the number.

The sponsor decision was explicit: **do not lower the floors, write the tests.** Gate 0 required measuring
honestly *before* acting on that, and specifically required confirming or refuting the hypothesis that
~164,000 of the counted lines were generated code.

## Investigation

**The generated-code hypothesis is REFUTED.** The repository contains:

- zero C# files carrying an `<auto-generated>` header
- zero `*.Designer.cs` files
- `docs/api/*.json` — OpenAPI specs, which are JSON data, never compiled, never in a coverage report

**The actual cause is the gate's own arithmetic.** `coverage-gate.sh` walked every `coverage.cobertura.xml`
and added up every line of every class:

```python
for f in files:
    for cls in ...:
        for ln in ...:
            val += 1; cov += hit
```

`dotnet test` on a solution writes **one report per test assembly**, and each report describes every
assembly that test project loaded — not only the code it owns. So `libs/authz`, `libs/auth`, `libs/events`
and each service's `Domain` were counted once per test project that referenced them. Measured on the real
data: **161 files appear in more than one report, one of them in 28.**

Two consequences, and the second is what made it look like a collapse:

1. The denominator tracks the number of *test projects*, not the amount of code.
2. A project that merely **loads** a library without exercising it contributes that library's full line
   count with almost no hits. Every test assembly added therefore pushed the percentage **down**. Phases
   19–21 added test projects; the number fell; no code got worse.

That also explains the asymmetry the phase prompt flagged — overall fell 19 points while domain fell 11.
Domain code is far less widely referenced across test projects, so it was double-counted less.

**The proof is arithmetic, not opinion.** The old gate reported **22,625 domain lines**, while the entire
`Domain` layer contains **12,488 physical source lines** — blanks, braces and comments included, none of
which is ever a coverable sequence point. A count of unique coverable lines cannot exceed the number of
lines in the files they come from. The denominator was inflated roughly threefold.

## Decision

1. **Measure by union, not by sum.** `tools/ci/coverage-report.py` resolves each cobertura entry to a
   canonical repo-relative path (reports use different `<source>` roots), keys every line by
   `(file, line)`, counts it **once**, and marks it covered if **any** run covered it.
2. **Exclude test code from the denominator.** Measuring how much of a test suite the test suite executes
   is a tautology; coverlet includes it by default. Production code only.
3. **Exclude nothing else.** `tools/ci/coverage-exclusions.txt` is deliberately empty. Nothing needed
   excluding, because the problem was never what was counted — it was how many times.
4. **The floors do not move.** Still 58 domain / 45 overall. Only the arithmetic changed.
5. **Publish per-module coverage on every run**, pass or fail, to the job summary — a collapse hiding
   behind an unrelated red step is exactly how this went unseen for a month.
6. **Guard the denominator like the floor.** `tools/ci/check-coverage-exclusions.py` rejects any added
   exclusion unless the commit cites an ADR that exists and names the path, and refuses `Domain/`, a whole
   service or a whole tree regardless of paperwork.

## The numbers

Measured locally over the full solution with `--with-db` (2,141 passed, 0 failed, 1 skipped; 32 reports):

| Metric | Old gate (naive sum) | Honest merge | Floor | Verdict |
|---|---|---|---|---|
| **domain** | 46.9% *(10,620/22,625 in CI)* | **82.5%** (5,773/7,000) | 58 | **PASS** |
| **overall** | 25.7% *(47,920/186,464 in CI)* | **50.7%** (19,306/38,071) | 45 | **PASS** |

Reproducing the old arithmetic on the same local data gives **24.9% (26,250/105,405)** — the same defect
CI saw. The absolute naive totals differ between CI and local (Release vs Debug sequence points); the
honest figures are what the corrected gate will publish on the next CI run.

**Domain coverage is 82.5% — above the 58% floor and above the ≥80% target in `CLAUDE.md`.** The floors
were never breached. The suite did not regress. The ruler was wrong.

## Consequences

- **Gate 3's stated target is already met** and must be re-aimed. Writing tests to raise domain from
  "46.9%" would have been work against a number that never existed. The per-module report shows where the
  real exposure is, which the aggregate was hiding:

  | Module | Layer | Coverage |
  |---|---|---|
  | `services/notification` | Api | 0.0% |
  | `services/orders` | Api | 1.3% |
  | `services/patient` | Api | 2.3% |
  | `services/profile` | Api | 3.2% |
  | `services/reporting` | Api | 5.8% |
  | `services/policy` | Api | 6.2% |

  Domain logic is well covered; **the endpoint layer is barely covered at all** — and that is where PHI
  projection and money paths actually execute. Gate 3 should be ordered by the AUDIT-R2 findings against
  those layers, as the phase prompt already intends ("raising the number is not the goal").

- **A percentage that moves for reasons unrelated to code quality is worse than no percentage**, because it
  is acted upon. This one nearly cost a sprint of tests aimed at a phantom regression, and under time
  pressure would have justified lowering a floor that was never breached.

- The auto-raise ratchet (Gate 1.4) now has a trustworthy input. With domain at 82.5% against a floor of
  58, the ratchet has substantial slack to take up.
